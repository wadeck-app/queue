# queue-sdk: one way to push events, with a versioned protocol

Status: draft v2 for validation, reviewed against the code (review fixes folded in). Nothing is implemented.

## Goal

Other CLIs and apps push events to the queue through `@wadeck-app/queue-sdk` instead of hand-written HTTP. The push protocol carries a version number, so the daemon and the SDK evolve without breaking integrations that are not updated together.

## Why

orchestrator's hand-written publisher lost every event silently: no `Authorization` header (401), no `cwd` (500), and `fetch(...).catch` never sees an HTTP error status. Each new integration would repeat the same mistakes.

## Decisions

| Topic | Decision |
|---|---|
| Package | `packages/queue-sdk`, `@wadeck-app/queue-sdk`, zero runtime dependencies, Node >= 22 |
| Surface | `createQueuePublisher(options)` returning `publish`, `publishAndWait`, `flush`, `status` |
| Failures | Never throw, never block the caller; every failure is reported with an actionable message |
| Dependencies | None at runtime, and none on `queue-cli`, not even as a devDependency. The SDK only checks that a `queue` executable is installed (PATH lookup) and runs it; the CLI is never bundled or imported |
| Daemon stopped | It stops itself 60-70 s after going idle. The SDK finds `queue` on PATH, runs `queue start` (constant arguments, idempotent), waits for the daemon, then POSTs over HTTP. If `queue` is not found, the event is reported as dropped |
| Payload transport | Always HTTP. The payload never goes through a command line or a shell |
| Protocol | Integer negotiated from `GET /version` (`queueProtocol: {min, max}`); sent in the push body only when above 1 |
| Compatibility | Daemon accepts the current and the previous protocol; changes inside a protocol are additive only |
| Contract tests | Recorded wire fixtures per protocol, replayed against the real service and the SDK |
| Publication | GitHub Packages, exactly like `queue-cli`: same registry, same `publishConfig`, same `GITHUB_TOKEN`, same workflow |
| OS support | Windows, macOS, Linux: no shell except to run `queue.cmd` on Windows, no POSIX-only calls, tests run on all three |

## Facts the design rests on (verified in the code)

- `POST /push` needs `Authorization: Bearer <contents of <configDir>/health_token>`; auth runs before the handler, so a 401 means nothing was queued.
- `PushRequest` is `{ event, payload, timeout?, cwd, replayOf? }`; omitting `cwd` gives HTTP 500 (observed live).
- `<configDir>/config.port` is JSON `{ sdkVersion, port, pid, startedAt }`, written while the daemon runs and removed on a clean stop only (a crash leaves it, and `health_token` is never removed). The daemon binds the first free port from 47910 to 47920.
- `GET /version` needs no token; it returns `version`, `pid`, `config_dir`, `sdkVersion`, `port` plus whatever `versionExtra()` adds (standard fields win).
- The daemon stops itself when `wal.pendingCount() === 0` and no dispatch is active for 60 s, checked every 10 s; entries with status `failed` do not count as pending.
- The daemon replies `{ ok: true, result }`; the SDK unwraps `result`.
- `before*` events are dispatched synchronously: the HTTP call lasts up to the request `timeout` (default 30 s).
- `queue start` starts the daemon when it is not running and exits 0 once it answers (5 s limit); it is idempotent. On Windows `queue` is `queue.cmd`; the shim sets stdio to `ignore` when not on a TTY, so only the exit code and the daemon state can be relied on.
- `singleton-daemon-kit` has its own `sdkVersion` (1) for the port file and auth handshake. It is separate from the push protocol.

## Package layout

```
packages/queue-sdk/
  package.json        name @wadeck-app/queue-sdk, not private, exports map, files: dist
  src/index.ts        public API only
  src/publisher.ts    createQueuePublisher, flush, bounded in-flight queue
  src/wire.ts         protocol constants, request/response types
  src/configDir.ts    QUEUE_CONFIG_DIR, XDG_CONFIG_HOME/queue, ~/.config/queue (empty variables ignored)
  src/daemon.ts       port file, liveness, /version check, start via `queue start`
  src/report.ts       failure reporting
  contract/           recorded fixtures, one folder per protocol number
```

`queue-core` is a devDependency only (a test keeps `configDir.ts` equal to `getQueueConfigDir`); the SDK never imports it at runtime. The `pretest` script builds `queue-core`, like the other packages. Module format: ESM and CJS builds behind an `exports` map; confirm what orchestrator, flow and task use before step 2.

## API

```ts
const queue = createQueuePublisher({
  cwd,          // default process.cwd(): selects the project's .queue/subscribers.yml and the project name
  configDir,    // default resolved like the CLI
  timeoutMs,    // HTTP timeout for fire-and-forget pushes, default 5000
  maxPending,   // in-flight bound, default 100; overflow is reported and dropped
  silent,       // true: no default console output (onError still called)
  onError,      // receives every failure
  onWarning,    // receives daemon deprecation notices
});

queue.publish(event, payload, { cwd? });          // fire and forget, returns void
await queue.publishAndWait(event, payload, { cwd?, timeoutMs? });
// -> { status: 'queued' | 'dispatched' | 'dropped' | 'unknown', eventId?, result?, reason? }
await queue.flush();                              // resolves when every in-flight push has settled
await queue.status();                             // { available, daemonVersion?, protocol?, reason? }
```

- `publishAndWait` never rejects. For `before*` events its default timeout is the request `timeout` (default 30 s) plus 5 s.
- `publish` does not keep the process alive after `process.exit()`: callers that exit call `await queue.flush()` first.
- `status: 'unknown'` means the request may have reached the daemon (connection reset, timeout); it is never retried.
- A daemon `aborted` answer maps to `dropped` with the daemon's reason.

## Reaching the daemon safely

1. Read `config.port`. Absent, or its pid is not alive and the port does not answer: the daemon is stopped.
2. Call `GET /version` (no token) and require `pid` and `config_dir` to match the port file. A mismatch means a stale file and a reused port: treat as stopped. The token is never sent before this check passes.
3. Cache the verified `(port, pid)` and the `queueProtocol` range for the publisher's life; re-verify after any connection error or 401.
4. Stopped: look for `queue` on PATH (PATH entries x PATHEXT on Windows, plain executable bit elsewhere; pure Node, no `which` dependency). Not found: report `dropped` with "queue is not installed or not on PATH". Found: run it once with `start` (single flight across concurrent publishes; fixed argv, `shell: true` only for a `.cmd` or `.bat` file on Windows with the resolved path quoted, `windowsHide: true`, `QUEUE_CONFIG_DIR` passed through the environment), then poll step 1-2 for up to 5 s. Non-zero exit or no daemon after 5 s: report `dropped` with the exit code.
5. Read the token from `health_token` on each use of a new verified daemon; on 401 re-read once and retry once.

Retries and fallback apply only to "daemon stopped / refused". A connection reset or timeout is `unknown`, reported and not retried: the event may already be in the WAL and there is no idempotency key yet.

## Protocol v1

Request body of `push`:

```json
{ "event": "job.started", "payload": {}, "cwd": "C:/repo" }
```

From protocol 2 on, the body also carries `"protocol": 2`.

| Rule | Behaviour |
|---|---|
| `protocol` absent | Treated as 1: every client that exists today keeps working |
| Daemon without `queueProtocol` in `/version` | Treated as `{min: 1, max: 1}` |
| SDK range vs daemon range | SDK sends the highest protocol both support; no overlap is reported with both ranges and what to update |
| `protocol` outside the daemon's range (a client that skipped negotiation) | `PushResponse.status: 'rejected'`, `reason`, `supported: { min, max }` |
| Deprecated but supported protocol | Accepted; the response carries `warnings: string[]`, surfaced once each through `onWarning` |
| New response fields | Additive; the SDK ignores unknown fields |
| Breaking change | New protocol number; the previous one stays supported for at least one release cycle, listed in `docs/push-protocol.md` |

Protocol 1 is today's behaviour, so the SDK works against every daemon that exists. Negotiation therefore does not depend on the old daemon knowing about `rejected`: the range comes from `/version`, and a missing range means 1. The version lives in the body, not in an HTTP header, because the `push` handler never sees headers (they belong to `singleton-daemon-kit`).

## Failure handling

| Situation | SDK behaviour | Message gives |
|---|---|---|
| No port file, process gone, or connection refused | Start via `queue start`, then push | Daemon stopped, started on demand |
| `queue` not found or `queue start` fails | `dropped` | "queue is not installed or not on PATH: install queue-cli", exit code |
| No `health_token` | `dropped` | Path searched, `QUEUE_CONFIG_DIR` hint |
| `/version` pid or config dir mismatch | Treat as stopped | Stale port file |
| 401 | Re-read the token, retry once | Token mismatch |
| 400, 404, non-JSON answer | `dropped` | Status and body excerpt |
| 500 / `aborted` | `dropped` | The daemon's reason verbatim (e.g. invalid `subscribers.yml`) |
| `rejected`, or no protocol overlap | `dropped`, no retry | Both ranges and the package to update |
| Connection reset, timeout | `unknown`, no retry | "may have been queued" and the timeout |
| Payload not JSON-serialisable | `dropped` | Which property failed |
| In-flight bound exceeded | `dropped` | `maxPending` value |

Reporting: `onError` gets every failure. The default output (`console.warn` unless `silent`) is deduplicated per publisher by failure kind plus reason, and the key resets on the first success.

## Daemon-side changes

- `QueueService.push` validates `protocol` (integer, in range), answers `rejected` with `supported`, adds `warnings` for a deprecated protocol.
- `PushResponse.status` gains `'rejected'`; `queue push`, `app-module-queue` and `queue-relay-client` must treat it as a failure (today `queue push` only special-cases `aborted` and would print "queued"). Tests for each.
- `queue-cli` passes `queueProtocol: { min, max }` through `versionExtra`.
- `PUSH_PROTOCOL_MIN` and `PUSH_PROTOCOL_MAX` live in `queue-core`; the SDK has its own copy, and a test keeps both equal.

## Tests

- SDK against a fake daemon: every row of the failure table, token re-read on 401, stale port file with a reused port (token not sent), single-flight start under concurrent publishes, `flush`, `maxPending` overflow, invalid `protocol` values, `before*` timeout, no throw ever; the start path with a fake `queue.cmd` and a fake `queue` executable on PATH (Windows and POSIX).
- The SDK test suite runs on Windows, macOS and Linux (see "OS support").
- Contract fixtures per protocol number, with `eventId`, timestamps and `cwd` normalised, replayed against the real `createQueueService`.
- New SDK against an old daemon: a `/version` and `push` fixture recorded from the released daemon (no `queueProtocol`, no `rejected`).
- `configDir.ts` equals `getQueueConfigDir` for the environment combinations, including empty variables.
- Integration: real daemon from `queue-cli`, push, stop, push again (SDK restarts it), published-shape import from `dist`.

## Publication

Same mechanism as `queue-cli` (`ci/scripts/generate-platform-packages.sh` and the `publish` job), nothing new:

- `package.json` carries `"publishConfig": { "@wadeck-app:registry": "https://npm.pkg.github.com/" }`, the value the platform packages already use.
- The `publish` job already runs `setup-node` with `registry-url: https://npm.pkg.github.com`, `scope: @wadeck-app` and `NODE_AUTH_TOKEN: GITHUB_TOKEN`. New steps: `npm pkg set version=<computed version>` in `packages/queue-sdk`, then `npm publish --tag <dist_tag>` there, after the main package.
- Root `build`, `test`, `clean` scripts get `queue-sdk` before `queue-cli`.
- Consumers install it the way they install `queue-cli` and the kit (scope mapped to GitHub Packages in their `.npmrc`).
- Package fields: `repository`, `exports`, `files` excluding tests.

## OS support (Windows, macOS, Linux)

| Concern | Rule |
|---|---|
| Starting the daemon | `queue start` with constant arguments. Windows, measured on the dev machine with Node 24: `spawn('queue')` without a shell gives ENOENT, `spawn('queue.cmd')` without a shell gives EINVAL, with a shell it runs; so ENOENT cannot be used to detect a missing CLI, the SDK does its own PATH lookup first. `windowsHide: true`. macOS and Linux: no shell. The only inputs are constants; `configDir` goes through the environment, never the command line |
| Process liveness | A pid check can be a false negative on Windows with MSYS2-started processes (the kit's client has the same guard). Alive = pid alive OR the port answers `/version` with the matching pid |
| Paths | `configDir` with `path.join`, `os.homedir()`; empty environment variables ignored; no hard-coded separators; the `cwd` sent is the OS-native path, the daemon already handles both forms |
| Port file and token | Plain files read with `fs`; no file locks, no signals, no `kill` |
| Output of `queue start` | Not parsed (non-TTY shim discards it on every OS); success is verified by polling the daemon |
| Line endings | Token and port file read with `trim()` and JSON parse |

The current CI runs on `ubuntu-latest` only, so Windows and macOS behaviour would be untested. The `build-and-test` job gets a matrix `[ubuntu-latest, windows-latest, macos-latest]` for the `queue-sdk` tests only (the rest of the repository stays on Linux). Tests that depend on the platform (fake `queue.cmd` on Windows, fake executable on POSIX) are skipped on the other platforms by an explicit `describe.skipIf(process.platform !== ...)` with the reason in its name, never silently.

## Open questions for you

1. Deprecation window: "current and previous protocol, at least one release cycle", or a fixed duration?
2. An event whose daemon cannot be started (`queue` missing) is lost and reported; a local spool file replayed by the daemon would avoid it but changes the daemon's architecture. Left out. Acceptable?

## Out of scope

Starting the daemon without the CLI, subscribing to or reading events, an idempotency key (can be added later as an optional field of protocol 1), event-name conventions beyond the suggestion `<source>.<verb>`.
